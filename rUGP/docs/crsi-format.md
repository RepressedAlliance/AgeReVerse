# CRsi：从帧表到原生像素的编解码原理

本文记录 PM Steam/AGES 7 已观察配置的可复现规格。目标是像 Cr6Ti、CRip007/008、
CRmt 一样，把“能替换”推进到独立实现、原生交叉验证及明确的适用边界。
制作成品状态见[《再诞》双段说明](../games/photonmelodies/video-localization/README.md)。

## 结论和范围

CRsi 是带时间信息的压缩帧序列。它不是 MP4，也不是 CRmt 缩放图片层。
其 codec-1 把图像分成 2×2 块，编码空间预测、亮度细节、色度及帧间修正量。
复用图片格式研究的是部分码字和 codec-0 路径，不是整个影片算法。

现有 C 实现无需游戏 EXE、Windows 图形接口、Unicorn 或 Python：

- `crsi_container.c`：限定父头、混合宽度帧表、完整帧计划读写。
- `crsi_codec.c`：四种已观察 codec-1 配置的解码，以及 0x0575 研究编码器。
- `crsi_lossless.c`：不透明 0x03ff 无损编码和解码。
- `crsi_tool.c`：独立检查器和指定帧导出工具；导出会从最近独立帧开始。

Python 的职责是字幕、视频素材组织及工具调用。`portable_codec.py` 只绑定明确提供的
C 库；`native_crsi.py` 是以合法本地 EXE 为依据的独立研究 oracle，不是播放器组件。
C 代码是重建算法，不是加载原版函数或把原版机器码包装成 DLL。
完整对象提取和顺序 FFV1 导出由 [crsi_workflow](../tools/video/README.md) 编排，
调用既有容器解析器和同一 C 核心，避免以私有脚本作为公开流程的必要步骤。

## 容器：对象头、索引、载荷

本次七个已知对象都采用以下 26 字节父头。整数均为小端。

| 偏移 | 长度 | 已验证含义／约束 |
| --- | --- | --- |
| 0 | 10 | 已观察签名 `00 01 01 00 00 00 00 00 00 00`；不能当作跨版本通用魔数 |
| 10 | 2 | 宽 |
| 12 | 2 | 高 |
| 14 | 4 | 已观察值 0；保留，不命名为已知功能 |
| 18 | 2 | rate，默认帧率为 rate/100 |
| 20 | 4 | 已观察值 0；保留 |
| 24 | 2 | 帧数；当前实现拒绝扩展计数标记 65535 |

随后是所有帧的索引表，最后才是连续载荷区。每条索引为：

```text
uint8 flags             bit 0：独立帧
uint32 offset           相对整个载荷区起点，不是相对本行
uint16 reserved         本范围为 0
uint16 mode
[uint16 parameter]      仅 ((mode >> 10) & 7) == 1 时存在
uint32 payload_length
```

codec-0 行是 13 字节，codec-1 行是 15 字节。混用时每一行分别计算，不能固定乘 15。
改用 0x03ff 后，表长、载荷起点和后续 offset 都会变化。
归档放置对齐不属于 CRsi 对象长度。C/Python 解析器都检查连续偏移、载荷边界和尾部闭合。

低层 `crsi_write()` 接受**完整帧计划**，保持父头和帧数，重算表和偏移；调用方必须保证
预测依赖正确。制作器 `rebuild()` 另有依赖闭合检查，不能用低层写入成功替代它。

## mode 和 parameter 不是两个任意的“画质等级”

```text
b_bits = (mode & 7) + 1
g_bits = ((mode >> 3) & 7) + 1
r_bits = ((mode >> 6) & 7) + 1
bit 9  = 标量 alpha 路径选择
codec  = (mode >> 10) & 7
```

这里沿用原配置中的 B/G/R 字段称呼；codec-1 内部将其用于亮度／色度量化步长，
不能直接当作 RGB565 一类像素布局。

| 已观察 mode/parameter | 三个宽度 | 本次来源 |
| --- | --- | --- |
| 0x0575 / 8 | 6/7/6 | 四段《再诞》及其他影片主体 |
| 0x056d / 32767 | 6/6/6 | 同卷其他影片中的部分独立帧 |
| 0x052c / 32767 | 5/6/5 | 同上 |
| 0x0524 / 32767 | 5/5/5 | 同上 |
| 0x03ff / 无 | 8/8/8 + bit 9 | 汉化无损替换路线 |

**parameter 在已审计 codec-1 独立帧算法中是长重复段附加修正码的触发阈值。**
当重复段长度达到 parameter 时，额外读 6 位颜色微调码。
8 表示长度至少 8 的重复段需要读取；32767 在当前尺寸下使这个分支不触发。
它不是帧率，也不能未经证明称为通用压缩质量参数。

## codec-1 的空间结构

码流按最低有效位优先读，原生读取器使用 16 位补充和 32 位前瞻。
C 实现按边界读位，不需要加载原版查找表或越界前瞻。每次处理两行、两个像素：

```text
TL  TR
BL  BR
```

每块维护 `(Y,U,V)`，对应右下角 BR 的基色。块行开头左侧状态为 `(128,0,0)`，
上方状态数组在帧开始时清零；这个数组属于**本帧空间预测**，不跨帧保存。

字面段与重复段交替。每行先读字面段长度；一行结束时不再读取下一段。
段长度 1 只需一位；更长的长度使用交错数据位／继续位的可变长整数。

字面块首先选择复制上方状态，或者更新空间预测：

1. 独立帧的 Y 预测为左右／上下状态平均，色度平均另带原版舍入项。
2. 依赖帧采用对应的差分量化掩码，不使用同一个舍入项。
3. 分别读取可选的有符号 Y、V、U 修正。0x0575 的 Y 步长为 2，色度步长为 16。
4. 选择平坦块或四像素细节；依赖帧还可选择从前帧该块的 BR 广播基底。

四像素细节不编码四套独立色度：BR 是当前基色，TR 从上方基色与 BR 预测，
BL 从左方基色与 BR 预测，TL 从前一 TR 与当前 TR 预测。
每个细节像素使用亮度修正，色度使用相邻状态平均。这是有损色度重建，
不是“每块一色”，也不是 DCT/JPEG。

细节码有 8 个短码和一个 7 位逃逸值。下表按实际读取顺序写位：

| 代码号 | 位序列 |
| --- | --- |
| 0 / 1 | `00001` / `00010` |
| 2 / 3 | `0011` / `011` |
| 4 / 5 | `1` / `010` |
| 6 / 7 | `0010` / `00011` |
| 逃逸 | `00000` + 7 位值；增量为 `value*4-256` |

短码的增量还依赖预测端点亮度差 `d`。`|d|<24` 使用固定码本；其他值使用：

```text
scale = (10 / (abs(d) + 25) + 0.16) * d
delta = floor((code - 4) * scale + d / 2 + 0.5)
```

这不是可随意交换求值顺序的数学表达式。原版 SSE2 的双精度舍入使
`d=-225,code=7` 和 `d=225,code=1` 对重排乘法敏感；C 实现保持原顺序，构建禁用浮点融合。

重复段沿用末块的基色。独立帧达到上述阈值时，6 位修正码分别选择：
Y `{0,1,2,4}`，两个色度各 `{-12,-4,0,4}`。不能漏读这 6 位，否则其后整帧码流错位。

## 从内部颜色到原生 BGRX

忽略中间饱和边界时，主要转换为以下定点式；`>>16` 必须是有符号向下取整。
最终每个字节钳制到 0–255。

```text
B = Y + ((U * 29032) >> 16)
G = Y + ((U * -5630) >> 16) + ((V * -11702) >> 16)
R = Y + ((V * 22970) >> 16)
X = Y + ((V * -11702) >> 16)
```

第四字节 X 是该原生计算的输出，不能解释为 PNG alpha。
此次完整核对比较 B、G、R、X 四字节，而非只比较可见 RGB。

还必须保留一个 MMX 打包细节：U 修正使用的 16 位查表结果同时包含“值”和“码长”。
`PSLLQ 40` 把码长移到了相邻 V 字内；5 位色度配置右移后，长度至少 8 的码字会使 V
额外加 1。6 位色度配置中这部分恰好移成 0，所以只测《再诞》不会发现它。

公开合成回归载荷 `70 57 02 00` 表示一个 2×2 平坦块、U 修正 -40。
原版解码输出每像素：0x0575/0x056d 为 `00 76 40 40`，0x052c/0x0524 为
`00 ac 40 3f`。这是指令与独立原生实验共同确认的兼容行为，不应“修正”为理想公式。

## 帧间预测：为什么改前帧会影响后帧

独立帧直接写入转换后的块。依赖帧将转换结果解释为以 128 为中心的修正量：

```text
new_byte = clamp(previous_byte + 2 * (decoded_byte - 128), 0, 255)
```

原实现执行两次相同方向的有符号饱和加法；对该范围等价于上式。
部分块保留每个位置的前帧基底，另一种模式先把前帧 BR 广播到该块再加修正。
本次已审计配置没有运动向量复制，也不需要外部视频解码库。

因此：只改一帧、随后继续用原依赖帧，会把原修正量加到不同的图像上。
原先的无损制作器一直重建到下一个原独立帧才允许复用。
新有损编码器则必须以**自己刚解出的重建图像**作为下一帧参考，不能使用理想源图，
否则会产生预测漂移。C API 显式返回重建表面用于这种反馈。

## 0x03ff：无损字幕制作路线

该路径复用 CRip008 kind-3 的标量 MSB 码流语法：alpha 段、字面／重复段、
上行复制、带上一绿色增量预测的颜色残差。CRsi 使用 B,G,R,0x80 原生布局；
不能直接套用图片工具特有的 RGBA 通道转换。

当前 C 接口只接受全不透明图像并显式拒绝其他 alpha 配置。
它与既有 compact producer 使用相同段选择，人工样本及两张实际画面输出逐字节相同，
并已分别通过原版解码。它不损失抗锯齿灰阶，适合现有字幕成果。

现有双段补丁偏大，是因为大量改帧选用了独立无损路线，而不是因为使用 Python。
0x0575 研究编码器能写独立和依赖帧，但未复原原编码器的码率分配、关键帧选择与压缩优化。
它的重建在原生解码器上完全一致，不代表与输入 RGB 无损，也不代表字幕质量已获批准。

## 时间、声音与归档路由

PM `0x5814b0` 调用 `MulDiv(frame,100000,rate)`，得到默认帧时间（毫秒）。
rate=3000 即 30 fps；整数时间会交替舍入，不能逐帧累加固定 33 ms 代替绝对帧公式。
这建立默认帧时钟，不解释播放器的全部控制状态及启动时刻。

声音在独立 `COptimizedObs` 中，通过脚本中的 `CPmBgm` 先启动；
`CPmVideoRef` 再选择 CRsi。图像语言分支选择日文或 Translation 对象。
CRsi 内没有可供重封装的音轨，也没有 MP4 式音视频共用的交织时间戳。

替换以完整 CRsi 对象进入既有 RUO，保留父引用、脚本、帧率和原音轨。
两段实际隔离播放已验证；此前录制测得约 0.37/0.42 秒的固定音画起点差，
尚无未修改版同条件对照，不能判断其来源。此次编解码研究没有重新操作游戏，
也没有把离线字节一致提升为绝对音画同步证明。
