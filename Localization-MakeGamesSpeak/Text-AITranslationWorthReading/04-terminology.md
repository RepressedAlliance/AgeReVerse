# 04 · 章节术语工作流

[规则顺序](README.md) · 上一步：[03 表字段](03-table-schemas.md) · 下一步：[05 初译](05-translation.md)

本文规定每个游戏或章节开始前和翻译过程中的术语确认、冻结与同步方式。目标是在当前范围内保持一致，并把可复用的确认术语沉淀到对应目标语言的公共术语表。

## 1. 文件和角色

- 当前简体中文公共表：[`../glossaries/muv-luv.ja-zh-Hans.csv`](../Glossaries-KeepItConsistent/muv-luv.ja-zh-Hans.csv)
- 生效表使用 `jp,cn,context` 三列；新语言必须新建独立文件和目标列，不能覆盖简体中文表。
- 每作仅加载本作`project.toml`明确指定的表；Muv-Luv七作加载系列通用表和本作专表，君望只加载独立的[本作术语表](../../AGE2/games/kiminozo/terminology/README.md)。各作互不继承专表；语境基线不作为自动替换字典。入口和历史边界见[术语目录](../Glossaries-KeepItConsistent/README.md)。
- 拟声片段、普通词和句子片段不是强制术语。`context` 的人物/机型/完整说话人限制必须遵守，严禁对正文进行无语境的批量替换。
- 公共表只保留稳定术语对；理由、状态、来源和审核讨论保存在候选记录或 pull request 中。
- 本作公开基线由 project.toml 的 terminology_baseline 指定，保存采用译法、候选、理由和篇章范围；terminology_evidence 指定原始来源记录，保留原状态及出现次数。完整官方例句留在本地，不随基线公开。
- 术语表与基线必须分开计数；旧表的来源记录不得仅因未命中筛选而消失。候选、语境限定与确认不能互相冒充。
- 仓库维护者负责公共表、跨游戏协调和最终同步。
- 单个章节的变更只处理本章术语，不直接修改其他章节正文。

## 2. 哪些内容属于术语

应优先扫描：

- 人名、姓氏、昵称和称号。
- 国家、组织、部队、机构和派系。
- 军衔、职务和固定称谓。
- 机体、兵器、装备、设施和技术名词。
- 作战名、计划名、地名和事件名。
- 有命名感的固定表达、反复短语和作品内梗。
- 重要カタカナ词、外语词和缩写。

普通动词、形容词和只出现一次的日常表达通常不进入总术语表。

## 3. 章节开工前的全章扫描

正文初译开始前，先在合法本机源数据中扫描本章全部 JP 文本：

1. 提取候选术语及其出现次数和典型上下文。对影响检索和采用的别名、写法变体及语境限制，在章节候选记录中保留对应关系和可定位的用例；字符相似不能作为同一对象的依据。
2. 与公共总表逐项比对。
3. 分类为：
   - `confirmed`：总表已有且适用于本章。
   - `candidate`：总表没有，需要确认译法。
   - `contextual`：同一 JP 可能因语境采用不同中文，需要记录适用条件。
   - `question`：含义、指代或固定写法仍不确定。
4. 对高频、关键剧情和跨章节术语优先确认。
5. 形成“本章术语基线”，记录日期或版本，随后才开始批量初译。

章节开工时要确认的是专名和固定表达，不需要让维护者或审校者逐个审批普通词句。

接手已有章节时可以复用仍适用的全章扫描和基线，只补查来源、规则或语境发生变化的部分；
不因更换批次或审核者重新扫描全章、重新建立同一基线。

## 4. 译法确认依据

译法判断顺序：

1. 本章已冻结基线和当前目标语言公共表中已经合并、且适用于该语境的译法。
2. 作品内 JP 上下文和官方日文设定。
3. 已有可靠中文惯用译名或经确认采用的中文资料。
4. 在语义明确的前提下，根据人名、专名、称号等类别决定音译、意译或保留原文，并遵守[最高原则](../principles.md)：保留原作已有英文，日文改用英文需确实适合。真实工作人员署名保留原写法，无官方中文译名的曲目保留原题；不要套用虚构角色译名规则，也不要把项目中文候选当成官方译名。英文版独有素材的含义用对应日语语音听译确认。

其中第 3、4 项描述当前简体中文目标；其他语言应换成对应语言的可靠资料和专名规则。英文槽、旧译文和模糊匹配不能作为原文含义的最终依据。网络资料只能作为可审查证据，不能越过 JP 原文和已经合并的项目决定。

## 5. 翻译中的术语处理

1. 每批开始前检查本批术语是否都在本章基线中。
2. 新出现的专名先加入章节候选记录，不能在不同批次随意采用不同译法。
3. 拿不准时标记 `question`，不得硬猜或静默替换。
4. 已冻结术语若需修改，必须记录旧译、新译、原因和影响范围。
5. 修改跨章节公共术语前，由维护者检查 TDA00-03、帝都燃烧篇、Photon 及其他受影响范围。
6. 术语变更后应重新检查本章所有出现位置，不能只改当前一句；按 [07 修改反查](07-change-impact.md) 记录需要同步的位置、语境例外和范围外待交接事项。

## 6. 冻结和版本更新

“冻结”表示当前章节按这版术语推进，并不表示永远不能修改。

需要更新基线时：

1. 先确认新译法。
2. 记录受影响的 JP 词条和章节范围。
3. 更新章节术语基线版本。
4. 扫描本章所有旧译变体。
5. 若属于可复用专名，再由维护者同步到对应目标语言的公共总表。

不得在没有记录的情况下直接覆盖已确认术语。

### 公开基线字段与状态

现行术语表集中放在`Localization-MakeGamesSpeak/Glossaries-KeepItConsistent/`；基线CSV放在各作品的`terminology/`中，由本作`project.toml`的`terminology_baseline`指定。基线保留来源差异和语境，不作为自动替换字典加载。

基线是本作术语表的父集：保留全部本作确认术语的来源与适用范围，同时包含语境项、候选和待核问题。条目提升为术语后，不从基线删除。分开存放不表示内容互相排除；同一日文的多份来源或不同语境可以各保留一条记录。

主基线用于日常阅读和程序处理；来源表用于追溯。相同日文、中文及类别合并来源，使用条件一并保留；不同中文或不同待核状态不合并。每条现行术语在主表只出现一次，中文及完整使用限制与术语表一致，不再为了区分现行和历史而复制整组记录。

主基线使用六列：

| 字段 | 含义 |
| --- | --- |
| `jp` | 原文日文写法，保留全角／半角等差异 |
| `cn` | 该条采用或参考的中文；空值表示尚未提供中文 |
| `kind` | `term`为现行术语；`context`为语境参考；`candidate`为候选；`question`为待核问题；`reference`为同一日文的其他来源／语境译法 |
| `chapter` | 已知篇章或适用范围；来源未定位时如实注明 |
| `basis` | 现行术语的完整使用限制，或参考／候选的原有依据；多份不同依据分别保留 |
| `evidence_rows` | 对应来源表的记录编号，以分号分隔，含表头从1计；程序逐项核对关联 |

`term`依据现行术语表判断，不以旧来源写着“已确认”来决定。`reference`不自动成为同一语境下可互换的译法；仍须看原依据。只在旧依据已明确标为误命中／普通表达或原已排除的记录不挤入主表，但完整留在来源表中。

来源表放在本作`terminology/history/`，使用原有九列。下列状态和出现次数只描述该来源当时的判断：

| 字段 | 含义 |
| --- | --- |
| `jp` | 该来源记录中的日文写法；不同写法可分别保留 |
| `cn` | 该记录的译法，可能是旧译或候选；空值表示来源没有提供中文 |
| `status` | 该条记录的处理状态，须结合理由和当前术语表判断 |
| `chapter` | 已知篇章或适用范围；未定位具体篇章时如实注明 |
| `source` | 原始来源标识；在恢复清单或修订记录中查对应文件及版本 |
| `source_row` | 来源表记录编号，通常含表头从1计；无表头TSV从1计，CRsa JSON用`section:index`。不是游戏台词编号，也不一定等于文件物理行号 |
| `source_status` | 来源原有状态或类别，不随本次整理状态一并覆盖 |
| `occurrences` | 来源提供的出现次数；空值表示未统计，不表示零次 |
| `basis` | 采用、限制、争议或排除的依据，以及后续决定 |

来源中的`confirmed`、`contextual`、`candidate`、`question`、`excluded`均保留原口径；其中“本作采用”“已确认”只描述当时的决定。历史差异不自动等于错译或弃用，仍须结合具体语境判断。

同一日文在不同语境下可以有不同中文；同一词的多份来源在来源表分别保留，在主表关联查阅。主基线条目数、来源记录数、去重后的日文写法数、现行术语数分开统计，都不能作为全文人工校对进度。

“去重后的日文写法数”按`jp`文字完全一致去重，不按概念合并；全角和半角仍分别计数。原文写法不因检索方便而改写。

可按类别查阅基线，不改动来源状态：

```powershell
python Localization-MakeGamesSpeak/Tools-LetToolsHandleRepetition/terminology.py tda00 --baseline --term ウィル
python Localization-MakeGamesSpeak/Tools-LetToolsHandleRepetition/terminology.py photonflowers --baseline --history --group noise
python Localization-MakeGamesSpeak/Tools-LetToolsHandleRepetition/terminology.py photonmelodies --baseline --group candidate
python Localization-MakeGamesSpeak/Tools-LetToolsHandleRepetition/terminology.py kiminozo --check-baseline
```

默认读取主基线；加`--history`读取原始来源。`--term`同时返回现行术语、主表条目和逐条关联的来源，不需要调用方解析说明文字。`--check-baseline`检查现行中文、完整使用限制、来源关联、不同译法和待核状态，防止漏项、错关联或误提升候选。读取工具也兼容尚未整理的旧九列基线。

旧来源中的出现次数保留原口径；重建资料中TDA按含词记录数、Photon按匹配次数计，不直接横向比较。官方完整例句不随公开基线发布；历史路径和计数描述当时状态，当前入口以项目清单为准。

## 7. 同步公共总表

满足以下条件的词条可以进入公共总表：

1. JP 和目标语言对应明确。
2. 译法已经确认。
3. 具有跨场景或跨章节复用价值。
4. 不依赖只在某一句成立的临时语境。

简体中文表同步时写 `jp,cn,context`，使用限制写在 `context`；详细来源、争议和审定理由留在候选记录、审计记录或 pull request 中。旧混合表与待确认项不参与加载。新语言使用自己的文件与目标列。

## 8. 章节术语完成标准

章节进入最终审核前，应满足：

1. 高频和关键专名都有明确译法或仍在可见的 `question` 清单中。
2. 同一术语没有无依据的多种目标语言变体。
3. 称谓差异可以由人物关系和场景解释。
4. 本章新增的可复用术语已提交维护者确认。
5. 公共总表与章节最终采用译法没有未说明的冲突。
