# 从初译到玩家反馈的完整本地化工作流

[English](workflow.en.md) · [返回本地化工作区](../README.md) · [规则顺序](README.md) · [源数据规则](02-source-data.md) · [术语规则](04-terminology.md) · [初译规则](05-translation.md) · [独立审核](06-review.md)

这套流程来自本项目实际完成 TDA、帝都燃烧篇和 Photon 文本时形成的方法。核心不是
“让 AI 把整张表翻译一遍”，而是把剧情理解、术语冻结、第一次翻译、第二次独立审核、
技术写回、实机检查和玩家反馈分成有证据的阶段。玩家反馈表明，这种分轮处理能明显减少
错译、称谓漂移、角色同声、控制符损坏和只在实际场景中才会暴露的问题；它不是对任何
旧译文质量的自动量化结论。

## 翻译最高原则

文本与图片共同遵守[日译中的最高原则](../principles.md)：日文译成中文，日文原版已有英文保留英文，日文只有确实更适合时才译成英文；官方英文版独有素材找到对应日语语音后听译成中文。听译案件保存语音定位与工作用转写，初译、独立二审和疑点处理都回到实际日语语音。找不到或听不清必要依据时保持待确认，不能用英文槽兜底。

全量核查后，按内容用途、玩家理解和原作表现区分应译与保留范围。大部分日文应译成中文；主要承担身份识别或原作表现作用、保留不妨碍必要理解的内容，以及在中文语境中可直接沿用的原文，可以说明理由后保留。同一句或同一张图的不同部分分别判断。曲名、署名、日期标记等只是常见例子，新内容同样按[通用判断方法](../principles.md#如何判断是否需要翻译)处理。保留范围、理由与确认依据随初译交接，独立二审逐项检查；不能用“消除所有日文”作为完成标准。

## 总流程

```text
合法提取与身份锁定
        ↓
通读剧情、建立人物关系与术语基线
        ↓
第一次翻译：按完整场景生成候选译文
        ↓
第二次独立审核：keep / revise / question
        ↓
解决 question、更新术语并按 07 反查关联修改
        ↓
AGE2 或 rUGP 技术绑定、写回与自动验证
        ↓
实机 QA：首次覆盖全路线，后续复查受影响范围
        ↓
维护者人工检查、修改发现的错误并复查结果
        ↓
完成制作，发布对应测试包
        ↓
发布后的玩家反馈与 ParaTranz 协作校对
        ↓
反馈回到原文、术语和场景重新复核，再发布新版本
```

任何一步通过，都不能替代它后面的步骤。中文读起来顺不等于日文理解正确；静态解码
成功不等于游戏运行成功；游戏能启动也不等于全文、图片和字体已经通过。

## 0. 冻结合法输入与稳定身份

开工先依次核对 [01 项目清单](01-game-project.md)、
[02 源数据](02-source-data.md)和 [03 表字段](03-table-schemas.md)，
确认本次使用的游戏、引擎、权威文件及字段映射。后续第 1—3 步分别应用 04 术语、
05 初译、06 独立审核；详细对应见[规范入口](README.md)。

1. 从自己合法拥有的游戏安装中提取源数据。
2. 记录游戏版本、Steam App ID、资源路径、对象 ID／偏移和源文件 SHA-256。
3. 不以工作站绝对路径或“第 123 行”作为唯一身份。
4. 公开表可以保留源字段哈希而不批量镜像官方全文；其他贡献者从自己的合法安装重新
   提取并按哈希连接。
5. AGE2 与 rUGP 的提取、写回和运行时路径必须分开。

输出：源资源清单、稳定 ID、源哈希、场景顺序，以及尚未识别的结构问题。

## 1. 第一次翻译前：先理解剧情并建立术语

不要随机抽一批行直接翻译。至少先完成：

- 按 route／scene 顺序阅读当前章节及必要前后文；
- 记录人物关系、身份差、称谓、口癖和当前情绪；
- 扫描人名、组织、军衔、机体、武器、作战名、地名和固定梗；
- 与[系列通用术语表](../Glossaries-Keep-It-Consistent/muv-luv.ja-zh-Hans.csv)
  合并已有决定；
- 新词先进入术语候选，不在正文里各自临时发明译名；
- 拿不准的剧情、说话人、称谓或术语先标为 `question`。

术语表不是翻译结束后的清理表，而是第一轮翻译开始前就要建立、随后持续修订的剧情
理解工具。

输出：章节概要、人物/称谓表、冻结术语基线、原文保留决定、待确认问题清单。

## 2. 第一次翻译：产生候选译文

第一次翻译按完整 scene 或自然剧情段推进。每行至少保留：

| 字段 | 作用 |
| --- | --- |
| `id`／`stable_id` | 不随排序变化的文本身份 |
| `resource_file`／`egpack`／`rio_file` | 回到游戏资源的位置 |
| `scene`、`speaker_jp` | 理解语境和说话人 |
| `source_text_sha256` | 锁定实际文本源字段；听译另记对应日语语音定位，不虚构 JP 槽或哈希 |
| `localized_text` 或现有表的等价列 | 候选译文 |
| `status` | `translated`、`question` 或 `blocked` |

这一轮的任务是准确理解日文并写出自然中文，不做技术写回。英语槽、旧中文、OCR 和机器
翻译只能用于发现问题，不能取代日文依据。英文版独有素材从对应日语语音听译，记录语音定位与转写疑点；原作已有英文及有理由采用的英文按最高原则处理。详细规则见[初译规则](05-translation.md)。

输出：候选译文、术语增量、问题清单、批次范围和下一批起点。

## 3. 第二次翻译／独立审核

第二轮不是在第一版中文上“润色一下”。审核者必须重新阅读日文、上下文和人物关系；听译案件重新听对应日语语音，不能只审第一轮转写。
逐句给出：

- `keep`：原候选可以保留；
- `revise`：提供修改后的译文以及关键理由；
- `question`：证据仍不足，明确还需要什么信息。

条件允许时使用不同人员、不同对话或至少完全独立的一轮判断。不能批量默认 `keep`，也
不能为了文风偏好做没有原文依据的同义改写。`revise` 与 `question` 是审核结论，不是
第一次翻译的状态。

输出：逐句结论、修改前后文本、修改理由、尚未解决的问题和审核统计。完整标准见
[独立审核规则](06-review.md)。

## 4. 解决 `question` 并再次冻结术语

`question` 不能在打包前悄悄消失。按需要补充：

- 后续剧情与相同用词的其他场景；
- 日文语音、说话人和表情；
- 游戏截图及实际调用位置；
- 官方设定或系列内已确认用法；
- 资源槽、控制符和图片上下文。

确认后按 [07 修改反查](07-change-impact.md) 检查关联位置，同步受影响的正文、
公共术语表和作内术语表，保留有语境依据的差异。仍无法判断的项目保持
阻塞，不能靠英文槽或“读起来差不多”强行定稿。

输出：已解决问题、仍阻塞问题、术语表版本和跨章节一致性报告。

## 5. 技术绑定与写回

语义定稿后才进入引擎层：

- AGE2：从合法 `pack.bin` 提取 FPD 成员，按稳定身份生成 EGPACK 修改，处理 UI、WebP
  和字体，以 LocalAppData 松散覆盖发布；
- rUGP：从 ICI/RIO 定位 CRsa、Cr6Ti、CRip 等对象，选择 RUO 静态覆盖或严格版本绑定的
  运行时，检查容量、父引用、路由和 8311 等约束。

每次写回都要保留输入哈希、输出哈希、工具版本和允许变化的字段。能解包不等于能封包，
单个样本成功也不能推出同类型全部对象成功。

## 6. 自动质量门

发布候选应覆盖以下适用检查；日常改文先运行相关检查，未受影响且仍适用于当前候选的结果可以复用。源版本、工具或共用依赖变化时扩大到其影响范围，不要求每次局部修改都重跑全套：

- 稳定 ID、行数、重复与缺失；
- 源哈希仍与锁定版本一致；
- 控制符、编码、容量、偏移和父引用；
- 术语一致性与禁用旧译名；
- 全量译文的字体覆盖；
- 图片尺寸、模式、透明度、哈希和同组排版；
- 包内文件清单、安装目标和可回滚性；
- 未混入原始容器、工作站路径、密钥、测试图或来源不明字体。

自动测试证明的是明确写入断言的条件，不等同于实机结论。

## 7. 实机 QA

首次建立对应游戏、语言和资源方案的实机覆盖时，至少覆盖标题、设置、第一段台词、存读档、回看、所有路线、选项、说话人、成就、字体、
每类修改图片和补丁卸载。图片需要检查的不只是“能看到”：还包括异色、撕裂、透明度、
错槽、英文回退、日文/translation 路由差异和 shared/common 端点。

后续局部修订检查修改位置、必要上下文和受影响功能，不因一句译文变化重走所有路线。
游戏版本、写回方案、字体或共用资源变化时扩大相关覆盖；无法确认影响范围时先调查，
必要时进行全面回归。已有覆盖及复用依据应在版本记录中说明，缺失的检查不能视为通过。
发布包的构建、安装与卸载验证仍按对应引擎要求执行。

每个问题应记录游戏、版本、路线、日期/章节、前后台词、截图、稳定资源 ID 和复现步骤。

## 8. 发布前的维护者人工收尾

这是制作流程的最后一步。AI 初译、独立复核和技术检查完成后，维护者仍会人工检查译文
措辞、称谓、术语、缺漏、排版、图片文字及实机显示，修改发现的错误、确认采用方案并
按 [07 修改反查](07-change-impact.md) 复查结果，然后发布对应版本。
修改影响资源时须重新写回并复跑相关检查。

玩家下载包已经包含该版本发布前落实的人工修正，不是等待发布后才开始处理的 AI 初稿。
这不等于维护者完成了全篇专业日中校对；实际检查覆盖范围及尚未解决的问题仍按版本记录。

## 9. 发布后的玩家反馈与 ParaTranz 校对

ParaTranz 主要用于发布后其他参与者的日文对照校对与后续修订，与发布前的制作和维护者
人工收尾分开。在制作品也可提前开放协作。平台改文须由维护者确认、检查并纳入后续发布，
同步到 GitHub 不代表玩家手中的安装包已经更新。

玩家反馈是第三层真实环境验证，不是随手在 Release 里改一个文件。收到反馈后：

1. 先确认游戏、补丁版本、语言槽和是否安装其他 Mod；
2. 用截图、章节和前后台词定位稳定 ID；
3. 回到日文原文和术语基线判断是翻译、资源绑定、字体、图片还是安装问题；
4. 修改可维护源表或代码，而不是只修生成的 EGPACK／RIO／WebP；
5. 按 [07 修改反查](07-change-impact.md) 同步关联位置，重跑受影响的自动检查和场景；共用依赖变化或相关失败时扩大检查范围；
6. 在变更记录中说明修复，并生成新的可复现 Release。

## 10. 哪些内容进入公开仓库

应该公开：

- 稳定文本表、术语表和长期有效的审核状态；
- 图片文案、无字底/成品的合法发布清单、哈希和制作方法；
- 字体来源、许可证、覆盖报告和构建方法；
- 编解码器、打包工具、测试、错误复盘和可复现命令。

默认不公开：

- 原始游戏容器和完整官方资源；
- 临时提示词、聊天记录、失败批次和个人便签；
- 工作站路径、账号信息或无法说明来源的字体；
- 只对一次对话有意义、不能复现最终结果的中间产物。

图片生成/编辑提示只有在它直接影响可复现视觉结果时才记录在图片工作流或资产配方中；
普通文本翻译不需要公开每轮提示词，公开规则、数据状态和验证工具更重要。

## 11. 迁移到韩语、俄语等其他语言

复用的是阶段和身份体系，不是中文表达规则：

1. 从合法游戏重新提取并连接源哈希；
2. 新建 `ko`、`ru` 等独立目标文件，不覆盖日文或中文；
3. 为目标语言重建术语、称谓、标点和字体政策；
4. 完整执行两轮翻译、`question` 处理、技术写回、实机 QA、维护者人工收尾与发布，再进行后续协作修订。

开始方法见[新语言指南](new-locale.md)。

## English summary

The reusable method is a staged, evidence-backed loop: freeze legal source
identity; understand the story and establish terminology; produce a first
translation by complete scene; independently review every row as
`keep`/`revise`/`question`; resolve questions and re-freeze terminology; bind
through the correct engine; run automated and in-game QA; have the maintainer
check and correct remaining issues before release; then feed player
reports back into the maintained source rather than patching generated files.
